Meta Harness 位于 middleware 装配层。它读取 `meta_harness` 配置，在构建当前 Agent 时决定哪些 middleware 进入装配链；它不是运行期的 prompt 开关，也不是一个单独替代 Agent loop 的执行器。

middleware 负责注册工具、贡献系统提示词段落或挂接生命周期事件。Meta Harness 在这些组件构造之前做裁剪，因此关闭组件的影响不仅是少一段提示词，还包括对应工具和注册副作用不会进入当前装配结果。

## 配置控制装配

`meta_harness` 使用一个键值映射。`false` 值对应 middleware 名称，表示该组件不参与当前装配；段落覆盖属于另一种配置入口，不能把任意 `true` 键理解成自动加载文件。

例如关闭 `FilesystemMiddleware`、`TerminalMiddleware` 和 `McpMiddleware`，会从当前 middleware 链中移除这些能力的注册入口。Agent loop、模型调用和 session 基础设施不由这些开关关闭，它们仍然负责处理消息和执行回合。

```json
{
  "config": {
    "meta_harness": {
      "FilesystemMiddleware": false,
      "TerminalMiddleware": false,
      "McpMiddleware": false,
      "ToolSearch": false
    }
  }
}
```

## 组件关闭后的影响

不同 middleware 持有不同内容。关闭 `DefaultSystemPromptMiddleware` 会移除它贡献的基础系统提示词，关闭 `SkillsMiddleware` 会移除 Skills 相关提示词和注册工具；关闭 `HumanInTheLoopMiddleware` 则会影响 AskUserQuestion 相关能力。

这些变化不能只看最终工具列表判断。组件可能同时贡献提示词、工具和初始化回调，检查配置时应按 middleware 的持有范围确认影响；关闭 Permission 或 Human-in-the-Loop 也意味着当前 Agent 不再拥有相应的审批路径。

## 与 Minimal Agent 的关系

Minimal Agent 使用 Meta Harness 把默认装配收窄，再按任务需要打开少数 middleware。`example/minimal` 当前打开 MCP 和 ToolSearch，关闭多个默认能力，因此它适合验证一条明确的工具链，不等于一个默认安全配置。

MCP 只是 Minimal Agent 的一种外部工具来源。Meta Harness 先决定 MCP middleware 和 ToolSearch 是否存在，MCP 再提供 server 连接，ToolSearch 最后决定延迟工具如何被模型发现和执行；三层职责互不替代。

## 适合控制什么

Meta Harness 适合控制 Agent 的能力边界和装配成本。例如只保留工具搜索与一个外部工具来源，或者关闭不适用于当前运行环境的文件、网络和子代理能力。

它不替代远程 server 的权限校验，也不替代模型 provider 的安全策略。关闭本地 middleware 后，外部 MCP server 仍需独立限制工具输入、身份和副作用。

## 验证装配结果

配置修改发生在装配阶段，不能只通过下一轮 prompt 判断是否生效。应检查 middleware 链、最终工具列表和系统提示词投影；对 ToolSearch，还要确认搜索索引中是否存在预期的延迟工具。

一个可复现的验证方式是先列出期望存在和期望不存在的工具，再执行一次搜索和调用。若工具未注册，问题应回到配置键、middleware 名称和装配路径，而不是先修改系统提示词。
