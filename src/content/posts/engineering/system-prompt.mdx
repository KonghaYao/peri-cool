系统提示词属于 Agent 请求的静态上下文。Peri 在会话创建时收集提示词段落、agent 定义、语言和环境快照并冻结它们；用户消息、工具结果和异步通知在后续消息路径中追加，不会重新扫描这份基础上下文。

middleware 可以贡献系统提示词段落，但 middleware 是否进入装配链由独立的 Meta Harness 控制。本文只讨论提示词的组成、冻结和请求序列化；middleware 的启用、关闭和工具副作用见 [Meta Harness](/peri-cool/posts/engineering/meta-harness/)。

## 提示词的架构位置

段落文件位于 `peri-acp/prompts/sections/`，文件名去掉 `.md` 后就是段落 ID。`persona` 和 `language` 是装配时生成的段落，分别来自 agent 定义和语言配置；它们和文件段落一样进入同一套排序和渲染流程。

段落分为 Cached 和 Uncached 两个位置。`01_intro` 到 `06_tone_style` 位于缓存区，`07_runtime` 及之后位于非缓存区，`10_hitl`、`11_subagent`、`12_ask_user` 和 `13_skills` 由对应 middleware 提供；某个持有者未进入装配时，对应段落也不会出现。

## 会话创建时冻结

创建会话时，Peri 读取项目规则、skills 摘要、系统提示词、语言和环境信息，并生成有序的 system message。运行期文件变化不会改写已经创建的会话；新会话才会读取新的规则和段落。

冻结的目的不是让内容永远不变，而是让同一会话的基础上下文有明确生命周期。日期、项目指引和工具说明如果在每轮请求前重新扫描，模型看到的系统前缀可能在会话中途改变，也会降低请求缓存的复用条件。

## 请求前缀的确定性

Prompt Cache 能否复用，首先取决于序列化结果是否相同。Peri 使用稳定的段落顺序和工具名称顺序；共享工具表按名称排序收集，同一工具集合在不同请求中的数组顺序保持一致。

系统消息通过统一的分块入口发送给 Provider。缓存标记只描述哪个块可以缓存，不能修复段落顺序变化、动态内容漂移或工具数组重排；缓存关闭时，内部边界标记会在发送前移除，不会成为模型可见文本。

## 动态消息不进入基础段落

用户消息、工具调用结果、订阅通知和其他运行期事件使用消息队列追加。它们可能改变下一次请求的上下文，但不会回写会话创建时冻结的系统提示词。

这一区分也适用于子代理。主 Agent 和子代理经过同一个请求适配器，但子代理拥有自己的消息和工具视图；共享基础规则不等于共享全部运行期消息。

## 验证提示词装配

排查提示词问题时，应分别检查段落来源、装配顺序、会话创建时间和最终请求序列化结果。关闭某个 middleware 后，先确认它是否贡献对应段落，再判断模型是否仍收到其他 middleware 提供的规则。

如果问题只在跨轮次或跨会话出现，还要比较冻结前缀、动态消息边界和工具数组顺序。不要只通过模型回复推断提示词是否生效，最终请求记录和装配测试才是更直接的证据。
