两个语义相同的模型请求，只要工具数组顺序不同，就不是同一个请求前缀。Peri 还遇到过另一条分歧，子代理路径会拆分系统提示词的静态与动态部分，主 Agent 路径却把它们作为一个块发送。两边都设置缓存控制位，实际序列化结果仍然不同。

**Prompt Cache**复用模型请求开头的稳定内容。缓存标记只告诉 Provider 哪个块可以缓存，它不能让变化的块顺序、遗漏的分界或随机排列自动变稳定。确定性序列化必须先于缓存策略成立。

## 系统提示词路径使用同一分块规则

Peri 的系统提示词包含会话内稳定部分，也包含运行期动态部分。边界标记把两者分开，Provider 适配器据此生成系统块，并把缓存控制放在稳定块上。

历史实现有两条系统消息路径。由普通系统消息进入的路径会调用分块逻辑，主请求顶层 system 字段却直接生成单块。相同内容经不同入口得到不同请求结构，缓存控制位无法弥补这次分叉。

当前 Anthropic 请求构造先合并系统消息，再统一调用同一个分块器。带边界的静态块与后续动态内容按固定规则生成。关闭缓存时，边界标记会从普通系统文本中移除，不作为模型可见内容发送。

在两个调用点各复制一份分块代码不是稳定方案。后续边界规则变化时仍可能只修改其中一份。统一的序列化入口让主 Agent 与子代理共享同一份行为。

## 工具数组按名称保持稳定顺序

模型请求中的工具定义是数组，数组位置属于序列化结果。早期工具注册使用无序键值表，并直接遍历其中的值。进程重启或运行期新增工具触发重新散列后，相同工具集合可能产生不同数组顺序。

当前共享工具表使用有序键值表，工具名称成为稳定排序键。推理阶段从这张表收集工具引用和定义，发送到 Provider 的数组顺序因此不依赖随机散列状态。

只在最终 JSON 上排序也能得到稳定结果，却会把排序规则推迟到 Provider 适配层。其他消费工具列表的路径仍可能保留不同顺序。让注册表从源头确定顺序，减少了跨层复制规则的机会。

工具包装层仍要保持这个顺序。若过滤或装配阶段重新放入无序容器，最外层使用有序键值表也不能保证最终前缀稳定。跨请求复用的数据只要经过一层不确定收集，整个契约就失效。

## 冻结内容限制会话内前缀变化

确定性排序解决相同集合的序列化问题，不能阻止集合本身变化。Peri 在会话创建时冻结日期、项目指引、Skills 摘要和系统提示词，当前会话及其子代理复用这份数据，避免中途重读文件改变前缀。

运行期用户消息、工具执行结果和异步通知仍会变化，它们属于请求后段。缓存设计不要求整条请求静止，只要求计划复用的前缀内容和顺序可预测。

每轮重新扫描项目指引看似能获得更新内容，却会让同一会话的系统前缀随文件变化。Peri 选择在新会话读取新规则，运行中的会话继续使用创建时冻结的基础上下文。

## 契约测试固定分块与顺序

Anthropic 请求测试构造带动态边界的系统消息，检查静态块的缓存控制、动态内容位置和工具执行结果顺序。无缓存测试则确认边界标记不会泄露到普通系统文本。

工具顺序目前由共享工具表的有序类型和收集路径共同保证，架构标准要求修改注册或 Provider 请求体时比较相同输入的连续序列化结果。相关回归测试同时检查系统分块、边界清理与请求顺序。

仓库没有为这些修复提供同口径的缓存命中率、时延或成本对比。确定性序列化只是缓存可以复用相同前缀的正确性前提，Provider 是否命中还受模型、账户、请求窗口和服务端策略影响。

开头那两个语义相同的请求，需要在系统分块、工具内容和工具顺序上都相同。缓存标记只负责指出边界，Peri 必须先把边界前的字节稳定地生成出来。
