一个跨目录重构跑了很久，终端被关闭。再次打开 Peri 时，聊天记录还在，刚才的目标状态却不见了，后台任务也没有继续。表面上都是恢复长任务，实际丢失的是三类不同状态。**会话保存对话上下文，Goal 保存当前进程中的目标，Workflow journal 保存脚本流程的执行记录**。Peri 没有一个把三者全部包办的恢复开关。

## 会话恢复对话上下文

聊天被中断后，先从 `/threads` 找到旧会话，或在相同项目目录用 `peri --continue` 继续最近记录。恢复后先让 Peri 复述任务边界，再对照工作区检查实际 diff 和测试状态。会话记录能告诉 Agent 之前讨论了什么，也能保留工具事件。它不能证明运行时对象仍然存在。旧消息里写着后台检查正在运行，不代表新进程里还有那个任务。以下输入是演示示例，不是真实会话。

```text
继续这个会话。先不要修改文件。
请对照当前 git diff 和测试输出，列出已经完成、尚未完成、需要重新验证的部分。
```

这一步把恢复依据从聊天叙述拉回工作区。完整操作见[会话管理](/peri-cool/docs/guides/sessions/)，恢复后还应由本地版本控制确认文件状态。

## Goal 恢复任务方向

Goal 适合在多轮执行中保持一个明确目标和验收条件。当前 active goal 使用进程内存保存，关闭 Peri 后不会随着对话记录恢复。重新进入会话时，应根据现有证据重新声明目标，而不是假设旧 goal 仍然有效。验收条件也要一起重述，避免 Agent 只记住方向而丢失完成标准。以下输入是演示示例，不是真实会话。

```text
重新建立目标，完成 auth 模块的异步迁移。
当前工作区已有部分修改。先检查现状，再继续。
验收条件仍是公开 API 不变、目标测试通过、列出未运行检查。
```

Goal 完成时的辅助验证只查看最近一段对话。长会话临近完成时，把关键 diff、测试命令和剩余风险重新放进近期消息。细节见[管理长任务](/peri-cool/docs/features/long-running-tasks/)，最终仍以工作区和测试为准。

## Workflow 恢复固定流程

当任务本身是一段确定流程，例如逐目录审查、批量迁移或多阶段质量检查，Workflow 会把生命周期事件写入 journal。它保存的是脚本步骤与执行结果，不是对话的完整语义，也不替代仓库状态核验。恢复前，先在 `/workflows` 查看 run 与阶段状态，再确认脚本和输入没有改变。当前产品仍有命令与事件接线边界，不能把 journal 存在直接等同于所有场景都能无损续跑。设计背景见[工作流设计](/peri-cool/posts/engineering/workflow-design/)，用户入口见[Ultracode 工作流](/peri-cool/docs/features/ultracode-workflow/)。

<Aside type="caution" title="恢复不是回滚">
  会话、Goal 与 Workflow 都不会替你恢复外部系统。已经写入的文件、推送的分支、发送的请求和删除的数据，需要按各自系统的事实源检查。
</Aside>

## 三类状态决定恢复动作

| 中断后缺失的状态 | 先做什么 | 不应假设什么 |
| --- | --- | --- |
| 对话上下文 | 恢复会话，核对 diff 与测试 | 旧消息中的运行状态仍然有效 |
| 目标与验收条件 | 重新声明 Goal | active goal 已跨进程保存 |
| 固定流程进度 | 查看 Workflow run 与 journal | 所有节点都能自动无损续跑 |

如果三类状态都不可信，最稳妥的处理不是继续旧叙述，而是创建新会话，把工作区现状、已验证证据和下一阶段目标重新交给 Peri。新会话从可核对的事实开始，不继承旧运行状态的假设。

## 恢复检查表

- 从版本控制确认哪些文件真的改变了。
- 从测试输出确认哪些验证真的运行过。
- 检查后台任务、Cron 和 Goal 是否仍存在于当前进程。
- 查看 Workflow run，而不是只读聊天里的进度汇报。
- 重新声明范围、禁止事项与完成条件。
- 在继续写入前先执行一个只读核对回合。

回到开头那个关闭终端的重构任务，正确动作不是寻找一个万能继续按钮。先恢复会话理解上下文，再重建 Goal 明确方向，只有固定脚本流程才检查 journal。三类状态分开核对，长任务才有可验证的续点。
